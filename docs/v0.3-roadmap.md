# dsh-prime-agent v0.3 路线：持久 RLM 计算环境

## 决策

v0.3 的第一优先级是持久计算环境，而不是照搬 Prime Agent 的 IPython 技术栈。

v0.2 已经提供 `prime_context`、DSH PTC/Code Mode、Subagent/Jobs 和次级 Continual Harness。PTC 本身已经交付 Prime 最有价值的控制面：模型只使用一个 `run_code`，在 TypeScript 程序里组合所有可见工具与递归 Agent；`prime_context` 又把大型数据移出模型上下文并按需读取。

剩余的高价值差距是连续计算：每次 `run_code` 结束后 JavaScript heap 都会销毁。它可以恢复 text、JSON 和 artifact reference，却不能继续使用上一轮定义的函数、对象、import、索引、client 或组合逻辑。Prime Agent 的优势来自以下能力共同作用，而不是 Python 语法本身：

1. 持久计算 namespace。
2. 模型上下文之外的可寻址数据。
3. 可程序化组合的工具和递归 Agent。
4. Host 拥有的权限、日志、取消与生命周期。
5. 失败后可观察、可恢复或诚实降级的状态。

因此 v0.3 的产品定义是：

> 模型继续只使用现有 DSH PTC/Code Mode；同一 Agent Session 的 `run_code` 进入同一个长期 TypeScript Realm，使函数、对象、module cache 和计算索引跨 turn 延续。

IPython 只作为理解 Prime 行为的参考实现，不进入产品路线。Context Capsule 与 Agent family 顺延到 v0.4，自动 refinement 闭环顺延到 v0.5。

## 两种持久状态

v0.3 必须明确区分活计算状态与可靠数据状态：

| 状态层 | 责任 | 保证 |
| --- | --- | --- |
| Persistent Code Realm | 函数、对象、import、索引、client、当前计算便利状态 | 同一活跃 Realm 跨 turn 保留；崩溃恢复按类型诚实降级 |
| `prime_context` | 明确命名的 text、JSON、artifact reference、大型输入和重要结果 | manifest/blob 原子持久化、版本、配额、检索与进程重启恢复 |
| `prime_refine` | 稳定路由与行为经验 | 证据化、乐观并发、事务历史和冲突安全回滚 |

Persistent Realm 不是 `prime_context` 的替代品，`prime_context` 也不是持久 heap 的等价替代品。

## 目标体验

v0.3 初版保留现有 async function body 兼容性，通过 runtime-owned `state` namespace 显式保存活对象：

```ts
// turn 1
state.indexRecords = (records: Array<{ id: string }>) =>
  new Map(records.map(record => [record.id, record]))

const source = await tools.prime_context({
  operation: 'get',
  key: 'records',
  pointer: '',
})

state.recordsById = state.indexRecords(source.value)
state.selectedIds = ['a', 'b', 'c']
return { indexed: state.recordsById.size }
```

```ts
// turn 2：不重新定义函数，不重新构建索引
const selected = state.selectedIds.map(id => state.recordsById.get(id))
const reviews = await Promise.all(selected.map(item => tools.subagent({
  description: `review ${item.id}`,
  prompt: JSON.stringify(item),
  run_in_background: false,
})))

state.reviews = reviews
return reviews
```

后续可以评估真正的 cell-like 顶层声明持久化，但不能为了表面像 REPL 而破坏现有 `run_code` 语义、取消边界或 TypeScript 工具兼容性。

## 为什么先做 Persistent TypeScript Realm

### 它最符合 DSH 原生边界

- DSH 已有 Worker Thread Code Runtime、Code Mode SDK、lossless JSON bridge、nested tool logging、并发调度、取消和输出治理。
- 其他插件工具已经自动进入 `tools` SDK，不需要重写 Python host bridge。
- 可以保留现有 `run_code` 工具名、TypeScript schema 和模型习惯。
- 部署只依赖 Node，不强制用户安装 Python、IPython、Jupyter transport 或独立 kernel environment。
- 改动集中在 continuity identity、worker pool 和 persistent state，而不是建立第二套控制面。

### IPython 只提供设计参考

- cell namespace 天然保存顶层变量、函数、class 和 import。
- interrupt 通常能在不立即杀死 Kernel 的情况下中断代码。
- `dill` 可以 best-effort snapshot 一部分函数和对象。
- Python 数据与研究生态更丰富，也与 Prime Agent 上游更接近。

这些性质用于校准 Persistent TypeScript Realm 的目标与诚实边界：顶层状态应连续，中断与硬终止的差异必须可见，可恢复与不可恢复状态必须区分。项目不实现 Python/IPython backend，也不维护 Jupyter transport、Python tools bridge 或第二套依赖与权限系统。

## 当前 DSH 缺少的 seam

当前 DSH `CodeRunRequest` 只有 `program`、`bindings` 和 `signal`。Worker Thread Runtime 每次 `run()` 创建一个 Worker，并在完成后终止；`dsh-tools` 调用 runtime 时也没有传 owning Agent identity。

因此 v0.3 首先要加入一个通用、最小、非 Prime 专属的连续性身份，例如：

```ts
interface CodeRunRequest {
  program: string
  bindings: CodeBindingNamespace[]
  signal?: AbortSignal
  continuity?: {
    key: string
  }
}
```

设计要求：

- `key` 是 runtime 使用的不透明稳定身份，由 DSH consumer 从 owning Agent/Session 导出。
- Runtime 不获得 Agent 对象、Session 对象、凭据、工具 registry 或宿主路径。
- 现有 stateless runtime 可以忽略 continuity；persistent runtime 必须明确要求它。
- key 落盘或进入诊断前使用带版本域的 hash，不直接作为文件名。
- Agent resume 使用相同 key；不同 Agent、fork 和 child 必须使用不同 key。
- 需要显式 `release(key)` 或等价 lifecycle 通知。若第一版缺少该 seam，runtime 必须用有界 LRU/idle TTL，并在服务 dispose 时清理全部 Realm。
- 不能使用 AsyncLocalStorage、全局 current-agent 或调用栈猜测 Session。

这项通用 seam 应优先进入 DSH Service Definition 和 Tools consumer，使将来的 TypeScript、Python 或其他 persistent backend 共用。

## Persistent Worker Pool

新增独立 runtime implementation，保留现有 stateless Worker Thread backend 的语义：

```text
DSH run_code consumer
  → CodeRunRequest(continuity.key, program, bindings, signal)
  → PersistentWorkerThreadRuntime
      → RealmPool[continuity.key]
          → long-lived Worker
          → persistent state namespace
          → stable tools proxy
          → optional data checkpoint
```

每个 continuity key 对应一个 Realm：

- 同一 Realm 的 program 串行执行，不能并发修改同一 heap。
- 不同 Realm 可以按配置并行。
- Worker 内 `state` 是不可替换的 null-prototype namespace，但其自有条目可以创建、更新和删除。
- 动态 import 的 module cache、保存在 `state` 中的函数、class instance、Map、Set 和 client 在 Worker 存活期间延续。
- Realm 记录 generation。Worker 被 kill/restart 后 generation 增加，模型能知道哪些 live-only 状态已经丢失。
- Runtime 服务 dispose 时停止 admission、终止活动 run、等待 nested calls 结算并清理所有 Worker。

## `state` Namespace 契约

初版不承诺自动捕获 async function 的全部局部变量；需要跨 turn 的值显式写入 `state`：

```ts
state.parser = buildParser(options)
state.records = new Map()
state.review = async (id: string) => {
  return tools.review_item({ id })
}
```

要求：

- `state` global 由 runtime 定义为 non-writable/non-configurable。
- namespace 自身使用 null prototype，`__proto__` 等名称只能作为普通 own key 或被明确拒绝，不能修改原型链。
- state key、总 key 数和 catalog 字符数有上限。
- 保存任意对象不代表可跨进程序列化。
- 保存的函数在下一轮调用 `tools.foo` 时，必须解析当前 run 的 bindings，不能缓存上一轮权限。
- `state.clear()`、按 key delete 和 Realm reset 需要明确操作；reset 整个 Realm 属于破坏性行为。
- prompt 用例必须鼓励只保存值得跨 turn 复用的计算状态，避免无界缓存。

真正的 top-level cell namespace 可以作为后续增强，但必须解决声明重定义、top-level return/await、source map、TypeScript 擦除和硬中断语义后才能替换显式 `state`。

## Stable `tools` Proxy

长期保存的函数可能引用 `tools`。因此 `tools` 不能是上一轮 binding functions 的永久闭包，而要是 Worker 内稳定 proxy：

1. 每个 run 分配新的 run id，并安装该 run 的 binding descriptor。
2. `tools.name(args)` 发送 run id、call id、tool name 与 lossless JSON args。
3. Host 只在该 run 仍活动且 tool 属于当前 Agent 可见集合时 dispatch。
4. DSH 继续执行 schema、权限、scope、日志、并发和取消检查。
5. run 结束后 binding table 立即失效；旧 call 明确失败。
6. 下一轮调用持久函数时，同一个 proxy 自动使用新的 active run id 和当前 bindings。

不变量：

- Worker 永远不能持有 Cordis Context、Agent、凭据或真实 host function。
- own-property lookup，不能通过 `constructor`/prototype 访问未声明 binding。
- 参数与结果继续使用 DSH lossless JSON 和大小/深度限制。
- detached task 不能在 run 结束后继续调用旧 tools bindings。
- 每个 nested tool call 继续进入 DSH 耐久日志。

## Turn、异步任务和取消

Prime 的活 Kernel 可以承载后台任务，但 DSH 的 tool logging 与 turn 生命周期目前围绕一次 `run_code` 调用关闭。v0.3 初版采用保守边界：

- 普通对象、函数、module cache 和显式 state 跨 turn 保留。
- 未被 DSH Jobs/Subagent 管理的 timer、Promise 和后台异步循环不得跨 run 继续调用 tools。
- 长任务应进入 DSH Subagent/Jobs，并把 handle 保存在 `state` 或 `prime_context`。
- cooperative abort 先通知当前 run。
- infinite loop 或拒绝 cooperative abort 的代码需要 terminate Worker；这会丢失该 Realm 的 live-only heap。
- Worker 被硬杀后，runtime 创建新 generation，恢复可 checkpoint 数据，并明确报告丢失项。

这一点是 Persistent JS 与 IPython 的真实差异：Node Worker 的可靠硬中断通常等于终止 Realm。v0.3 必须诚实暴露，不得声称所有函数/对象在 abort 或崩溃后仍存在。

## Checkpoint 与进程恢复

跨 turn 活状态与跨进程持久化是不同保证。

### 可以 checkpoint 的状态

Runtime 可以对 `state` 中可支持的数据做 best-effort checkpoint：

- lossless JSON 值可以可靠落盘。
- 经安全评审后，可以选择支持 Node/V8 serializable 的 Map、Set、Date、ArrayBuffer 和循环数据，但必须记录 runtime/version 兼容性。
- function、closure、Proxy、Promise、socket、stream、native handle 和大多数 client 默认 skipped。
- 每个 state key 独立处理，一个失败不能使全部 checkpoint 失败。

### checkpoint 契约

- payload 和 manifest 采用临时文件、完整性校验和原子替换。
- manifest 记录 schema/runtime/Node version、realm generation、saved、skipped、failed、bytes 和时间。
- 每 key、总 checkpoint、Realm 和全局磁盘分别设限。
- checkpoint 失败保留上一个有效版本。
- restore 只加载 runtime 自己生成且完整性通过的状态。
- 首个恢复后的 context 明确告诉模型 saved/restored/skipped/failed 和 generation change。
- 不自动重放历史 `run_code`，因为其中的 tool calls 可能有外部副作用。

需要跨进程可靠恢复的重要结果仍必须写入 `prime_context`。v0.3 的核心验收是跨 turn live persistence；任意 JS function/closure 的跨进程恢复不是完成条件。

## Realm Catalog

每轮动态 prompt 增加有界元数据，不注入完整对象：

```text
Persistent TypeScript realm generation 3:
- indexRecords: function (live only)
- recordsById: Map (12,431 entries; checkpoint skipped)
- selectedIds: Array (3 items; checkpointed)
- job: object (live only)
```

要求：

- 只读取 own property descriptor、内建安全 type tag 和有界 shape。
- 不调用任意对象的 `toString`、custom inspect、getter、iterator 或递归遍历。
- 不把 secret、完整值、宿主路径或 checkpoint payload 注入 prompt。
- catalog 条目和总字符数受配置限制。
- 明确区分 live、checkpointed、restored、skipped 和 lost。
- 提供 inspect、checkpoint、delete-key 和 reset 能力；reset 必须作用于精确 Realm。

## Realm Pool 与资源治理

最低配置项：

- `maxActiveRealms`
- `maxIdleMs`
- `maxRunMs`
- `maxWorkerOldGenerationMb`
- `maxOutputBytes`
- `maxHostCallsPerRun`
- `maxParallelHostCallsPerRun`
- `maxStateEntries`
- `maxRealmCatalogChars`
- `maxCheckpointBytes`
- `maxCheckpointValueBytes`
- `maxTotalCheckpointBytes`

行为要求：

- 达到 Realm 上限时明确 admission；优先 checkpoint 并回收 idle LRU Realm。
- 正在运行的 Realm 不因普通 LRU 被杀。
- idle TTL 只回收 Worker，是否保留 checkpoint 由状态策略决定。
- Worker crash 不能拖垮 DSH host。
- orphan Worker 有 owner marker 和启动/退出回收机制。
- Windows 与 Linux 至少各有进程生命周期测试。
- 资源限制属于准入和治理，不应让已接受的 `prime_context` 数据不可读。

## 安全边界

- Worker Thread isolation 不是权限沙箱；模型代码与 DSH host 属于同一 OS 进程/用户边界。
- tool authority 只通过每 run 当前 bindings 暴露。
- `state` 不能保存 host credential、Agent、Cordis Context 或真实 tool function。
- checkpoint 目录采用私有权限，continuity key 与宿主路径不进入模型上下文。
- bootstrap-only proxy、证书和进程环境仍由 DSH 启动策略拥有。
- Realm 恢复不能执行未验证的外部序列化 payload。
- 自定义 getter/Proxy/inspect 不能在 catalog 或 checkpoint discovery 阶段被隐式执行。

## 状态放置规则

| 内容 | 放置位置 |
| --- | --- |
| 大原始文档、JSON 数据集、artifact reference | `prime_context` |
| 当前分析函数、索引、解析器和 client | Persistent Realm `state` |
| 必须跨进程可靠恢复的重要结果 | `prime_context` |
| 可 best-effort checkpoint 的计算便利数据 | Realm `state` + checkpoint |
| 长期异步工作 | DSH Subagent/Jobs；handle 可放 `state` |
| 需要传给其他 Session/child 的内容 | 先显式序列化；v0.4 Capsule |
| 稳定路由与行为经验 | `prime_refine` |

## 实现阶段

### 阶段 1：DSH continuity seam

1. 先向 DSH 上游提出最小通用 request identity 和 release 生命周期契约；不维护宿主源码分叉。
2. 上游接受后，更新插件的 Code Runtime provider、测试和文档。
3. 保证现有 stateless Worker Thread runtime 行为不变。
4. 验证 Agent scope、fork、resume、compaction 和 delete 的 identity。

### 阶段 2：Persistent Worker 与 state

1. Realm pool 和每 Realm 串行执行。
2. 长期 Worker 多次接受 program，而不是 run 后退出。
3. runtime-owned `state` namespace。
4. stable `tools` proxy 和 per-run binding lease。
5. output、exception、timeout、abort 和 worker-exit 映射。

### 阶段 3：恢复与治理

1. Realm catalog 和 generation/lost 状态。
2. per-key best-effort checkpoint/restore。
3. LRU、TTL、heap 上限和 orphan 回收。
4. reset/delete/checkpoint 管理工具或命令。

### 阶段 4：产品化

1. Prime bundle 切换到 Persistent Worker runtime。
2. 精确的 system prompt 与 TypeScript SDK 示例。
3. 实际 Web/headless 两轮执行、abort、重启和恢复验证。
4. README、架构、上游差异手册、安全 review 和发布检查。

## 测试与验收

### 跨 turn 核心能力

- turn 1 把函数、class instance、Map、module 和对象保存到 `state`；turn 2 不重建即可使用。
- turn 1 保存引用 `tools` 的函数；turn 2 使用当前 Agent bindings 成功调用。
- Session A 与 B 的 Realm 完全隔离。
- 同一 Session 的并发 run 被串行化，不交叉污染 state。
- 不同 Session 可以受配额控制地并行。

### 权限与生命周期

- 工具在两轮之间被撤销后，持久函数不能通过旧 closure 继续调用。
- run 结束后 detached tool call 被拒绝并记录清楚。
- Subagent/Jobs 从持久函数调用时保持 DSH scope、日志和取消语义。
- Agent release、runtime dispose、idle eviction 和 crash 都能回收 Worker。

### 中断与恢复

- cooperative abort 尽可能保留 Realm。
- infinite loop 导致 hard terminate 时 generation 增加并明确报告 live-only state 丢失。
- 可 checkpoint 数据在 Worker/DSH 重启后恢复。
- function、client 等 skipped 项被准确报告，不影响其他 key。
- checkpoint 损坏或中断时保留上一个有效版本。

### 兼容性与发布

- 其他插件工具继续自动出现在 `tools` SDK。
- `prime_context` 和 `prime_refine` 在 Persistent Code Mode 下可用。
- 现有 stateless runtime 和 native mode 测试不回归。
- catalog 不触发 getter/Proxy/custom inspect，不泄露完整值或路径。
- typecheck、完整测试、build、publint、bundle dump 和实际 profile 探活通过。

## 明确不属于 v0.3

- 任何 Python/IPython Runtime、Kernel 或 Jupyter transport；它们只作为设计参考。
- 保证任意 JavaScript function、closure 或 live handle 跨进程恢复。
- 让未受 DSH 管理的后台 Promise 跨 turn 使用 tools。
- Context Capsule `share`/`mount`；顺延到 v0.4。
- 完整 Agent family message/list/send/delete 高保真适配；顺延到 v0.4。
- 自动 refinement proposal/review/apply/outcome；顺延到 v0.5。
- 复制 Prime Daemon、Worker registry 或 Agent Loop。
- 宣称 Worker Thread 是安全沙箱。

## 后续版本

### v0.4：Context Capsule 与 Agent Family

- 不可变 `share`/`mount`、显式父子上下文授权和只读 namespace。
- admission-first child handle、list/follow-up/collect/cancel/delete。
- child 主动 reply 优先 steer 到仍在运行的 parent 最近 step；parent 空闲时才启动新 turn。当前 DSH `subagent-report` 默认走 `followup` 后续轮次，因此先提出通用调度扩展点，不在插件中分叉 Agent inbox 或修改 DSH 源码。
- capsule/blob 引用生命周期、quarantine 与 GC。

### v0.5：学习闭环

- 从失败、用户纠正和稳定成功生成 refinement proposal。
- proposal、review、apply 和 outcome observation 分离。
- global 修改默认需要明确批准。
- 效果回归时提出 rollback 建议，不自动扩大权限。

## 完成定义

只有满足以下条件才能称为 v0.3 完成：

- 同一 Agent Session 的后续 turn 能直接使用先前放入 `state` 的函数、对象、import/module 和索引。
- Persistent function 使用当前 run/Agent bindings，不缓存旧权限。
- Worker hard terminate、crash 和 eviction 的状态损失被准确暴露，支持的数据得到 best-effort checkpoint 恢复。
- `prime_context` 继续承担显式可靠数据持久化，两种状态层责任清晰。
- Session 隔离、取消、资源上限、崩溃回收和 host dispose 经真实测试验证。
- 模型仍然只看到 `run_code`，没有嵌套第二代码控制面。
- 不复制 DSH Agent/Jobs/Session 生命周期，不宣称 Worker 是安全沙箱。
- typecheck、完整测试、build、publint、bundle dump、实际两轮执行与重启恢复全部通过。
